# Destination-edge parametric prototype design

## Intent

Add bounded authoring evidence for a nearby rule family without changing the
selected production generator, canonical Racket authority, or approval state.
The family keeps the original task's core reasoning: detect every column that
contains color `1`, erase all source `1`s, collapse multiplicity to one marker,
and preserve every non-`1` cell except at the chosen destination.

## Parameter

`destination_edge` is chosen once per episode from `bottom|top`.

- `bottom` is the original/default and must use the exact canonical Racket text.
- `top` changes only the destination-row predicate from the last row to row 0.

The demonstrations and queries in an episode share one value. Inputs are
generated by the selected generator's existing `canonical_scaffold` and
`counterexample` profiles and therefore need no parameter-dependent resampling.
Each retained episode has three demonstrations and four distinct queries, with
all seven inputs distinct. Public challenges contain labelled demonstrations and
query inputs only; hidden parameters, Racket programs, and query answers remain
private evidence. Public challenge filenames are SHA-256 identifiers of the exact visible
bytes, so setting order, seeds, private metadata, and query answers cannot name a
public challenge.

## Approaches considered

1. **Destination edge (`bottom|top`) — selected.** This is a meaningful direction
   parameter, preserves the column-collapse algorithm, and produces clear
   same-input differing witnesses.
2. **Destination color (`1` versus another color) — rejected.** It changes mostly
   output palette semantics and weakens the family's structural generalization.
3. **Destination row offset (`last` versus `second-last`) — rejected.** It is
   executable but less natural and less recognizable than an edge direction.

## Evidence and limits

The prototype includes exact materialized Racket for both settings, Racket-
executed labels, a Python parity mirror used only as a check, one complete
three-demo/four-query episode per setting, per-query rival checks against the
opposite setting, one shared-input witness, source/rule hashes, and redacted
public challenges. Duplicate visible payloads are rejected and public files are
written in visible-ID order. This is proposed task-local evidence, not a
production API, canonical repair, approval, or all-seed proof.
